The pitch for GitOps is elegant: your cluster's desired state lives in git. Push a change, the cluster converges. No `kubectl apply` from your laptop. No SSH. No "let me just fix this one thing in prod real quick." The repo is the truth and the cluster obeys.

The reality involves a non-trivial amount of YAML, a CI/CD pipeline that needs to be taught not to trigger itself, and at least one evening wondering why your image tags aren't updating. But once it works, it genuinely works. Push to main, go make coffee, come back to running pods.

## FluxCD

<a href={`${REPO}/infra/k3s/flux/clusters/rookery`}>FluxCD</a> watches the `main` branch of this repo. Every sixty seconds, it checks for new commits. When it finds one, it reconciles the manifests against the cluster's actual state and applies whatever differs.

The manifests are organized in two layers with an explicit dependency:

<CodeBlock language="yaml">{`# clusters/rookery/infrastructure.yaml
apiVersion: kustomize.toolkit.fluxcd.io/v1
kind: Kustomization
metadata:
  name: infrastructure
  namespace: flux-system
spec:
  interval: 1h
  path: ./infra/k3s/flux/infrastructure
  prune: true
  wait: true`}</CodeBlock>

<CodeBlock language="yaml">{`# clusters/rookery/apps.yaml
apiVersion: kustomize.toolkit.fluxcd.io/v1
kind: Kustomization
metadata:
  name: apps
  namespace: flux-system
spec:
  interval: 30m
  path: ./infra/k3s/flux/apps
  prune: true
  wait: true
  dependsOn:
    - name: infrastructure`}</CodeBlock>

`dependsOn` is doing the work here. Infrastructure—Prometheus, Grafana, Loki, Cloudflare Tunnel—must fully reconcile before applications deploy. Without this, your pods start before the monitoring stack exists or before the tunnel is ready to route traffic. On a single node where everything competes for the same resources, ordering matters more than the docs suggest.

## Smart Change Detection

This is a monorepo. The homepage, the API gateway, the user service, the dashboard—they all live in the same repo with shared TypeScript packages. A typo fix in a blog post should not rebuild the API gateway. A change to a shared utility should rebuild everything that imports it.

The <a href={`${REPO}/.github/workflows/build-images.yml`}>build pipeline</a> uses pnpm's workspace-aware filtering to figure out what actually changed:

<CodeBlock language="bash">{`# Get all packages affected by changes since the last commit
AFFECTED_PACKAGES=$(pnpm ls -r --depth -1 --filter="...[$BASE_REF]" --json \\
  | jq -r '.[].name')

# Check if a specific app or any of its dependencies were affected
check_package() {
  local pkg=$1
  local output_var=$2

  # Get this package's full dependency tree
  local trigger_packages=$(pnpm ls -r --depth -1 --filter="\${pkg}..." --json \\
    | jq -r '.[].name')

  # If any affected package is in the dependency tree, rebuild
  local found=false
  for affected in $AFFECTED_PACKAGES; do
    for trigger in $trigger_packages; do
      if [ "$affected" = "$trigger" ]; then
        found=true
        break 2
      fi
    done
  done

  echo "\${output_var}=$found" >> $GITHUB_OUTPUT
}

check_package "@app/www" "www_web"
check_package "@gateway/service" "api_service"
check_package "@users/service" "user_service"
# ...`}</CodeBlock>

The `...[HEAD~1]` filter syntax is pnpm's "what changed since this ref" query. It walks the dependency graph. If `@website/utils` changed, every package that depends on it shows up. The result is a set of booleans—`www_web=true`, `api_service=false`—that downstream build jobs use to decide what Docker images to build.

A blog post change: one image, two minutes. A shared package change: everything, five minutes. A CI-only change: nothing built at all. On a repo with six deployable services, skipping unnecessary builds saves real time and bandwidth.

## Slim Docker Images

Each service uses multi-stage builds with Turbo's <a href={`${REPO}/apps/www/Dockerfile`}>workspace pruning</a>:

<CodeBlock language="dockerfile">{`# Stage 1: Prune the monorepo to just this package's dependency tree
FROM node:24-alpine AS workspace-pruner
RUN corepack enable
RUN pnpm add -g turbo
COPY . .
RUN turbo prune @app/www --docker

# Stage 2: Install dependencies and build
FROM node:24-alpine AS builder
COPY --from=workspace-pruner /app/out/json/ .
COPY --from=workspace-pruner /app/out/pnpm-lock.yaml ./pnpm-lock.yaml
RUN pnpm install
COPY --from=workspace-pruner /app/out/full/ .
RUN pnpm --filter @app/www build:ssg

# Stage 3: Serve static files
FROM nginx:alpine
COPY --from=builder /app/apps/www/dist/client/ /usr/share/nginx/html/`}</CodeBlock>

`turbo prune --docker` generates a minimal subset of the monorepo—only the target package and its workspace dependencies. The final stage copies just the build output. No `node_modules`, no source files, no other workspace packages. The homepage image is nginx serving static HTML. It pulls in seconds.

## The Infinite Loop

A rite of passage for anyone wiring up GitOps with CI/CD: the deployment pipeline builds images and commits updated image tags to the repo. That commit triggers the pipeline. Which builds images. Which commits tags. Which triggers the pipeline. You notice when your GitHub Actions bill looks wrong.

The <a href={`${REPO}/.github/workflows/cd-selfhosted.yml`}>fix</a> is one line:

<CodeBlock language="yaml">{`jobs:
  update-flux-manifests:
    # Skip if triggered by the bot's own manifest update commit
    if: github.actor != 'github-actions[bot]'`}</CodeBlock>

When a human pushes to main, the pipeline runs. It builds the changed images, then a bot commits the new tags to the FluxCD manifests using `yq`:

<CodeBlock language="yaml">{`update_tag() {
  local file=$1
  local built=$2
  if [ "$built" = "true" ]; then
    yq e ".spec.values.image.tag = \\"$TAG\\"" -i "$file"
  fi
}

update_tag infra/k3s/flux/apps/www-web.yaml "$WWW_WEB_BUILT"
update_tag infra/k3s/flux/apps/api-service.yaml "$API_SERVICE_BUILT"
# ...`}</CodeBlock>

The bot's commit triggers the pipeline again—but the `if` condition catches it and the workflow exits. FluxCD sees the new commit, notices the image tags changed, and rolls out new pods. Loop broken. The image tags follow the pattern `selfhosted-sha-{commit_sha}`, so if something goes wrong, the tag is a direct link to the exact code running in the cluster.

## Secrets Without Git

The one thing you never commit is secrets. But in GitOps, the repo is the source of truth. So where do the Google OAuth credentials, JWT signing keys, and database passwords live?

FluxCD solves this with <a href={`${REPO}/infra/k3s/flux/apps/api-service.yaml`}>`valuesFrom`</a>. Secrets live in Kubernetes Secret resources, created once via `kubectl create secret`. The HelmRelease references them by name:

<CodeBlock language="yaml">{`valuesFrom:
  - kind: Secret
    name: api-service-secrets-values
    valuesKey: googleClientId
    targetPath: secrets.googleClientId
  - kind: Secret
    name: api-service-secrets-values
    valuesKey: googleClientSecret
    targetPath: secrets.googleClientSecret
  - kind: Secret
    name: api-service-secrets-values
    valuesKey: jwtSecret
    targetPath: secrets.jwtSecret`}</CodeBlock>

At deploy time, FluxCD reads the Secret values and injects them into the Helm chart's values. The git repo never contains the credentials. The cluster does. If you destroy the cluster, you recreate the secrets manually—which is fine, because there are four of them and you keep them in a password manager like a responsible adult.

## The Full Flow

<CodeBlock language="bash">{`git push origin main
# 1. GitHub Actions detects affected packages via pnpm workspace filter
# 2. Builds only the changed Docker images (~2-5 min)
# 3. Bot commits new image tags to FluxCD manifests
# 4. FluxCD detects new commit within 60 seconds
# 5. Reconciles: pulls images, rolls out deployments
# 6. Cloudflare Tunnel routes traffic to new pods`}</CodeBlock>

Push to production in under five minutes. Most of that is Docker builds. The actual rollout—FluxCD detecting the change, pulling the image, cycling the pod—takes about thirty seconds.

Setting all of this up took considerably longer than thirty seconds. But that's a one-time cost, and now deploying is the most boring part of my workflow. Which is exactly what deployment should be.
